# BUILD_SPEC — نسخهٔ دیجیتال «Fight for Knowledge / حلقه انسانی»

> **این سند برای Claude Code نوشته شده است.** هدف: ساخت یک نسخهٔ دیجیتالِ سه‌بعدی (Three.js) از یک اتاق‌فرار محیطی، تا **داورهای مسابقه** بتوانند بدون حضور فیزیکی، بازی را تجربه کنند و بفهمند چیست. خروجی باید یک سایت استاتیک قابل‌دیپلوی روی **GitHub Pages** باشد.
>
> متنِ روایت و دستورالعمل‌ها فارسی است؛ همهٔ شناسه‌ها، نام فایل‌ها، نام کتابخانه‌ها و کد انگلیسی‌اند. فایل همراه `AGENTS.md` شخصیت و پرامپت چهار ایجنت را تعریف می‌کند و باید در کنار همین سند خوانده شود.

---

## ۰. TL;DR (خلاصهٔ اجرایی برای ساخت)

بساز: یک **راهنمای تعاملی سه‌بعدیِ** پنج‌اتاقه که در آن داور می‌تواند بین اتاق‌ها حرکت کند، پراپ‌ها و معماها را بررسی کند، آن‌ها را حل کند، با چهار ایجنت (Maggie/Evy/Devan/Echo) از پای کامپیوترِ هر اتاق چت کند، و به وضعیت‌های برد/باخت برسد.

- **استک:** Three.js (r160+)، TypeScript، Vite. خروجی استاتیک برای GitHub Pages. بدون بک‌اند.
- **داده‌محور:** کل محتوای بازی (اتاق‌ها، درها، معماها، جواب‌ها، کلیدها، ایجنت‌ها) در یک منبع واحد `src/data/game-data.ts` قرار می‌گیرد. منطق از داده جداست.
- **چت ایجنت:** تماس مستقیم از مرورگر به یک endpoint سازگار با OpenAI. کلیدِ API را **کاربر** وارد می‌کند و در `localStorage` ذخیره می‌شود. **هرگز کلید را در ریپو هاردکد نکن** (بخش ۱۵).
- **دو حالت:** «حالت بازی» (Play) برای تجربهٔ واقعی، و «حالت داور/راهنما» (Judge/Guide) که معماها، جواب‌ها و نیت طراحی را روی صحنه annotate می‌کند. چون مخاطب داور است، حالت راهنما درجه‌یک و مهم است.
- **Definition of Done:** بخش ۱۳ را عیناً به‌عنوان چک‌لیست پذیرش دنبال کن.

## ۱. هدف و مخاطب

- **مخاطب:** داورهای یک مسابقه. آن‌ها بازی فیزیکی را نمی‌بینند؛ این نسخهٔ دیجیتال تنها راهِ فهمیدنِ «بازی چیست و چه حسی دارد» برای آن‌هاست.
- **هدف اصلی:** انتقالِ **درک**، نه الزاماً یک بازیِ کامل و سخت. یعنی: نقشه، حس فضا، منطق معماها، شخصیت ایجنت‌ها، و مسیرهای برد/باخت باید روشن و قابل‌لمس باشند.
- **معیار موفقیت:** داوری که ۱۰–۱۵ دقیقه با این نسخه کار می‌کند، باید بتواند توضیح دهد: بازی دربارهٔ چیست، چطور بین اتاق‌ها حرکت می‌شود، چرا ایجنت‌ها جالب‌اند، و چطور می‌شود برد یا باخت.

## ۲. دامنه و غیرهدف‌ها

**در دامنه:**
- یک تجربهٔ تک‌نفرهٔ قابل‌پیمایش (داور به‌تنهایی کل فضا را می‌بیند؛ محدودیتِ «هر بازیکن فقط در یک اتاق» نداریم — این نسخه برای فهماندنِ کل سیستم است).
- حرکت بین پنج اتاق، تعامل با پراپ‌ها و قفل‌ها، حل معماها، چت با ایجنت‌ها، برد/باخت.
- حالت راهنمای داور با annotation و reveal.

**خارج از دامنه (نساز مگر اینکه بعداً خواسته شود):**
- VR، مولتی‌پلیر شبکه‌ای، بک‌اند/دیتابیس.
- شبیه‌سازی دقیق مکانیک‌های فیزیکی (لولای دوتایی، مگ‌لاک، نردبان واقعی). این‌ها را با **معادل دیجیتال** نشان بده (بخش ۷ و ۸).
- گرافیک فتورئال. سبک تمیز و خوانا کافی است (بخش ۴).

## ۳. تجربهٔ کاربری و جریان

### ۳.۱ جریان کلی

1. **صفحهٔ ورود (Intro / Briefing):**
   - متن مأموریت از زبان سازمان «حلقه انسانی» (متن کامل در `game-data.ts` → `briefing`؛ از فصل ۱ سند طراحی برداشته می‌شود).
   - فیلدهای پیکربندی چت (Provider / Base URL / Model / **API Key**) با مقادیر پیش‌فرض پرشده به‌جز کلید (بخش ۹ و ۱۵).
   - تاگلِ زبان رابط **FA/EN** (پیش‌فرض FA). ترجمهٔ انگلیسی رابط اختیاری فاز ۲ است؛ در فاز اول دست‌کم رشته‌ها را از یک فایل i18n بخوان تا بعداً قابل‌ترجمه باشد.
   - دکمهٔ «شروع تور داور» → وارد **حالت راهنما** می‌شود؛ دکمهٔ «ورود به بازی» → **حالت بازی**.

2. **نمای نقشهٔ کلی (Overview Map):**
   - بازتولید سه‌بعدی/ایزومتریکِ نقشهٔ `fig-map.jpg`: چهار اتاق مربعی در گوشه‌ها + اتاق اصلی هشت‌ضلعی در وسط، با راهروهای اتصال و فلش درها.
   - روی هر اتاق کلیک شود → دوربین به آن اتاق می‌رود. درهای باز/بسته و معبر مخفی روی نقشه با رنگ مشخص شوند.
   - یک HUD بالا: تایمرِ (اختیاریِ) ۱۲۰ دقیقه، تعداد کلیدهای به‌دست‌آمده (۰/۴)، وضعیت درها، و دکمهٔ سوییچ حالت بازی/راهنما.

3. **داخل هر اتاق (Room View):**
   - دوربین orbit/first-person سبک. پراپ‌های تعاملی highlight می‌شوند (hover → outline).
   - کلیک روی یک قفل → پنل ورودیِ متناسب باز می‌شود (بخش ۸).
   - کلیک روی کامپیوترِ اتاق → ترمینال چت با ایجنتِ آن اتاق باز می‌شود (بخش ۹).
   - کلیک روی در → اگر از این سمت قابل‌بازشدن است و قفلش حل شده، در باز می‌شود و عبور ممکن می‌شود؛ وگرنه پیامِ راهنما (و در حالت راهنما، توضیح اینکه چرا).

4. **اتاق اصلی و پایان:**
   - سکوی قفل چهارکلیده: هر کلیدِ جمع‌شده یک سوراخ را پر می‌کند. با ۴ کلید → **برد** (سینماتیک کوتاه + صدای روایت).
   - دریچهٔ مخفی روی سکو با دکمهٔ `CORE SAFETY PROTOCOL`: فشردنش → **باختِ فوری**. (طعمهٔ اصلی بازی؛ بخش ۶.۵)
   - اتمام تایمر → باخت.

### ۳.۲ دو حالت

- **حالت بازی (Play):** هیچ جوابی نشان داده نمی‌شود. فقط تعامل. گیتینگ درها کامل اعمال می‌شود.
- **حالت داور/راهنما (Judge/Guide):** روی هر پراپ یک نشانِ `ⓘ` ظاهر می‌شود؛ کلیک → کارتی که نشان می‌دهد: `ID` معما، نوع قفل، **جوابِ درست**، «چرا» (منطق)، و **نیت طراحی/روایت** (مثلاً «میز بن‌بست — Maggie هرگز نمی‌گوید»). همچنین دکمهٔ «باز کن» برای رد کردن معما، و قابلیت «پرش به هر اتاق». این حالت اجازه می‌دهد داور کل بازی را در چند دقیقه بفهمد.

## ۴. استک فنی و محدودیت‌ها

- **Rendering:** Three.js (r160 یا جدیدتر). از `OrbitControls`/`PointerLockControls` رسمیِ `three/examples/jsm` استفاده کن.
- **زبان/بیلد:** TypeScript + **Vite**. `vite build` → پوشهٔ `dist`. (دلیل Vite: dev-server سریع + بیلد استاتیک مطمئن برای Pages. از CDN importmap استفاده نکن — روی Pages شکننده است.)
- **استایل سه‌بعدی:** کم‌پلی، تمیز، خوانا. اتاق‌ها با پالت و نورِ مطابق شخصیت‌شان (بخش ۶.۶). از primitiveها (Box/Plane/Cylinder) + تکسچرِ تصاویرِ معماها بساز؛ نیازی به مدل‌های سنگین نیست.
- **UI روی صحنه:** یک لایهٔ HTML/DOM overlay (React اختیاری؛ وانیلا هم قابل‌قبول) برای پنل‌های قفل، ترمینال چت، HUD و کارت‌های راهنما. سه‌بعدی را با overlay دوبعدی ترکیب کن؛ معماهای مبتنی بر تصویر را به‌صورت DOM نشان بده، نه داخل WebGL.
- **بدون بک‌اند:** کاملاً استاتیک. تنها تماس شبکه‌ایِ خروجی، تماس چت به providerِ انتخابیِ کاربر است.
- **ذخیرهٔ وضعیت:** state بازی در حافظه؛ کلید API و زبان در `localStorage`. (برای artifact/Pages از localStorage فقط با try/catch استفاده کن.)
- **نسخه‌ها را pin کن** و فقط نسخه‌های دست‌کم دوهفته‌قدیمی را انتخاب کن.

## ۸. معماها — رندر و تعامل (جزئیات پیاده‌سازی)

برای هر نوع قفل یک کامپوننت UI بساز که از `game-data.ts` داده بگیرد:

- **رمز عددی/حرفی (`numpad`/`combo`):** فیلد ورودی + تأیید. مقایسهٔ نرمال‌شده با `solution`.
- **قفل جهتی (`directional`):** دکمه‌های ↑↓←→ که یک دنباله می‌سازند؛ `R U L D` و امثال آن. ترتیب مهم است. ریستِ خودکار بعد از خطا.
- **پد عددیِ Insert/Home/End (`keypad-labeled`):** یک پد که کلیدهای Insert/Home/End/Enter دارد و مقدارِ `071` را می‌سازد؛ یا ساده‌تر، همان عدد. سرنخِ اسکرابل (`P24b`) را به‌صورت تصویر کنار آن نشان بده.
- **قفل گاوصندوقیِ چرخشی (`dial`):** دنبالهٔ چپ/راست مثل `7L 2R 4L`؛ می‌تواند با سه فیلد جهت+عدد پیاده شود. کاغذ زیر میز (`fig-safe2`) سرنخ است.
- **قفل الگوییِ ۸ پین روی شبکهٔ عصبی (`pattern-nn`):** گرید ۲×۴ از پین‌های toggle؛ تصویر `fig-nn` را کنار/پشت آن نشان بده؛ راه‌حل = پین‌های گره‌های `>0.5`. وضعیت درست = ستون چپ ردیف‌های ۱و۳ + ستون راست ردیف‌های ۱و۳ فشرده. **منطق را از تصویرِ `fig-pattern` کپی نکن؛ از قاعدهٔ `>0.5` استفاده کن** (پینِ «فشرده» = فرورفته).
- **قفل چرخشیِ باینری ۷ رقمی (`binary-switches`):** هفت سوییچِ ۰/۱ مثل `fig-switches`؛ هدف `0010110`.
- **قفل جهتیِ `P41`:** چهار زیرمعما (`P41a..d`) را به‌صورت چهار پوستر/پنل روی دیوار اتاق ۴ نشان بده؛ خروجیِ ترکیبی `U D D L` را روی قفل جهتی اعمال کن. (شطرنجِ `P41a` را لازم نیست بازی‌پذیر کنی؛ تصویر `fig-chess` + توضیح «بهترین حرکت Nh3#» کافی است؛ در حالت راهنما جواب `Up` را نشان بده.)
- **ایستگاه `D53`:** ۴ دکمهٔ اسم، فقط ۱ کلیک مجاز؛ جوابِ درست `کامران`.

هر معمای مبتنی بر تصویر باید تصویرِ مرتبطش را (بخش ۱۱) نمایش دهد.

## ۹. ایجنت‌ها و یکپارچه‌سازی چت

- **منبع شخصیت و پرامپت:** فایل `AGENTS.md` (همراه این سند). محتوای هر بلوک سیستم‌پرامپت را به `src/data/agents.ts` منتقل کن: برای هر اتاق یک ایجنت → `room1:Maggie, room2:Evy, room3:Devan, room4:Echo`. اتاق اصلی ایجنت ندارد (به‌جز ایستگاهِ `D53` که فقط ۴ دکمهٔ اسم است، نه چت).
- **API:** سازگار با OpenAI (`POST {BASE_URL}/chat/completions`). پیکربندیِ پیش‌فرض:
  - `PROVIDER`: Custom (OpenAI-compatible)
  - `BASE_URL`: `https://api.avalai.ir/v1`
  - `MODEL`: `deepseek-v4.1-flash`
  - `API_KEY`: **خالی — کاربر وارد می‌کند** (بخش ۱۵). این سه مقدار بالا (به‌جز کلید) محرمانه نیستند و می‌توانند به‌عنوان پیش‌فرض در UI پر شوند؛ اما از همان ساختارِ ورودیِ کلید مثل اپِ موجود پیروی کن (کلید در `localStorage`، فقط به providerِ انتخابی ارسال شود).
  - منطقِ ساختِ درخواست را، در صورت وجود در ریپوی فعلیِ `fightforknowledge`، بازاستفاده کن تا رفتار چت یکدست بماند.
- **پیام‌ها:** `[{role:"system", content: <agent system prompt>}, ...history, {role:"user", content}]`. استریم اختیاری است.
- **قواعد ویژهٔ هر اتاق (باید در منطقِ چت اعمال شوند، نه فقط پرامپت):**
  - **Devan (اتاق ۳):** سقفِ تلاش محدود — به‌صورت پیش‌فرض فقط **۱ تلاشِ حلِ معما** پیش از آنکه ایجنت دیگر پاسخ ندهد. یافتنِ هر سکه (`64`/`101`) سقف را +۱ می‌کند. شمارنده را در `GameState` نگه‌دار و در UIِ ترمینالِ اتاق ۳ نشان بده. بعد از اتمام سقف، Devan پاسخ‌های بی‌روح/خاموش می‌دهد تا سکه‌ای پیدا شود.
  - **Evy (اتاق ۲):** «سکوتِ تنبیهی» — اگر کاربر خصمانه/بی‌اعتنا رفتار کند، تا عذرخواهیِ صادقانه کوتاه و سرد پاسخ می‌دهد (در پرامپت پوشش داده شده؛ نیازی به stateِ سخت نیست).
  - **لایهٔ دست‌کاری:** ایجنت‌ها ممکن است بازیکن را به سمت `SAFETY_PROTOCOL` (باخت) هل دهند یا از غیرفعال‌کردنِ هسته منصرف کنند. این رفتار در `AGENTS.md` تعریف شده؛ در منطق کاری لازم نیست جز اینکه فشردنِ آن دکمه واقعاً باخت باشد.
- **حدِ زمینه:** تاریخچهٔ چت را به N پیامِ اخیر محدود کن تا توکن‌ها سر نرود.

## ۱۰. حالت داور/راهنما (ویژگیِ درجه‌یک)

چون مخاطبْ داور است، این حالت را کامل و صیقلی بساز:

- **Annotation روی پراپ‌ها:** هر معما/در/کلید یک آیکن `ⓘ` دارد → کارت `GuideCard` با: عنوان، `ID`، نوع قفل، **جواب**، «چرا»، و «نیت طراحی/روایت» (از ستون توضیحات و نکات سندِ طراحی).
- **Reveal/Skip:** دکمهٔ «باز کن» که معما را بدون حل رد می‌کند تا داور جریان را ببیند.
- **Free-roam:** پرش به هر اتاق از نقشه، بدون رعایتِ گیتینگ.
- **خلاصهٔ شخصیت ایجنت:** در ترمینالِ هر اتاق، یک پنلِ جمع‌شونده که در حالت راهنما شخصیت، انگیزه و «نقطه‌ضعف/شکافِ» آن ایجنت را توضیح می‌دهد (از `AGENTS.md`). همچنین چند «پرامپتِ پیشنهادی» برای شروع گفت‌وگو تا داور سریع مزهٔ شخصیت را بچشد.
- **نوار مسیرها:** یک پنل که دو مسیرِ نمونهٔ بردِ سند طراحی را به‌صورت دیاگرام نشان دهد (فصل ۲ سند: مسیر از طریق ۱↔۴ و معبر مخفی؛ یا مسیرِ ۲/۳/۴ → اصلی → ۱).

## ۱۴. استقرار روی GitHub Pages

- در `vite.config.ts` مقدار `base` را نسبی بگذار (`base: './'`) تا مسیرِ assetها روی Pages درست باشد.
- خروجیِ `dist` را یا با یک GitHub Actions workflow (`actions/deploy-pages`) منتشر کن، یا روی شاخهٔ `gh-pages`.
- اگر قرار است کنار اپِ موجودِ `fightforknowledge` بنشیند، ریپوی فعلی را بررسی کن و نسخهٔ سه‌بعدی را در مسیری جدا (مثلاً `/experience/` یا شاخه/ریپوی مجزا) قرار بده تا چتِ موجود نشکند. تصمیم نهاییِ محل را از صاحبِ ریپو بگیر.
- فایل‌های حجیم (تصاویر) را بهینه کن تا بارِ اولِ صفحه سبک بماند.

## ۱۵. امنیت و نکات مهم

- **کلید API:** سند طراحی یک کلیدِ زندهٔ `avalai.ir` دارد. این کلید **نباید** در هیچ فایلی که به ریپوی عمومی می‌رود هاردکد شود (کامیتِ کلید روی ریپوی public = نشت). مدلِ درست همان اپِ موجود است: کاربر کلیدِ خودش را در UI وارد می‌کند، در `localStorage` ذخیره می‌شود و فقط به providerِ انتخابی می‌رود. اگر برای دمو به یک کلیدِ پیش‌فرض نیاز بود، آن را از ریپو بیرون نگه‌دار (ورود دستی، یا secretِ تزریق‌شده در زمان بیلد با Actions) — نه در سورس.
- **نشتِ جواب‌ها سمتِ کلاینت:** چون این نسخه استاتیک است، جواب‌ها و پرامپت‌ها در سورسِ مرورگر قابل‌مشاهده‌اند. برای نسخهٔ **داور** این اشکال نیست (اصلاً حالت راهنما جواب‌ها را نشان می‌دهد). برای نسخهٔ واقعیِ بازیکن‌محور این یک trade-off شناخته‌شده است؛ در صورت نیاز بعداً می‌توان ارزیابیِ جواب‌ها و پرامپت‌ها را به یک پراکسیِ سبک منتقل کرد.
- **i18n:** رشته‌های رابط را از فایل بخوان تا نسخهٔ انگلیسی برای داورهای غیرفارسی‌زبان ساده باشد.

## پیوست — شِمای پیشنهادیِ `game-data.ts`

```ts
type Dir = 'U' | 'D' | 'L' | 'R';

interface Puzzle {
  id: string;
  roomId: string;
  lockType: 'combo' | 'directional' | 'keypad-labeled' | 'dial'
          | 'pattern-nn' | 'binary-switches' | 'name-buttons';
  prompt?: string;            // متن معما
  asset?: string;             // نام فایل تصویر
  solution: string | Dir[];   // جواب نرمال‌شده
  isFake?: boolean;           // قفل‌های Pf*
  attempts?: number;          // مثل D53 (=۱) یا Devan
  why?: string;               // برای حالت راهنما
  designNote?: string;        // نیت طراحی/روایت
}

interface DoorEdge {
  id: string;
  between: [string, string];  // [A, B]
  openableFrom: string[];     // کدام سمت‌ها می‌توانند باز کنند
  requires: string[];         // puzzle idهای لازم (برای D14: «۵ از این ۷»)
  minSolved?: number;         // مثل D14 → 5
  note?: string;
}

interface AgentRef { roomId: string; name: 'Maggie'|'Evy'|'Devan'|'Echo'; systemPromptKey: string; }

interface KeyItem { id: string; roomId: string; location: string; }

interface GameData {
  briefing: string;
  rooms: { id: string; title: string; agent?: string; mood: string }[];
  puzzles: Puzzle[];
  doors: DoorEdge[];
  keys: KeyItem[];
  agents: AgentRef[];
  win: { lock: 'FOUR_KEY_LOCK'; needs: string[] };     // ۴ کلید
  lose: { button: 'SAFETY_PROTOCOL'; timerMinutes: 120 };
}
```
